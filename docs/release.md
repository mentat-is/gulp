# Release process

gULP uses one release identity for the Python core, the bundled React source,
the GitHub Release, and the `gulp-core` and `gulp-ui` Docker images. The
identity consists of a `vMAJOR.MINOR.PATCH` Git tag and the full commit SHA
referenced by that tag.

The core is not published to PyPI. `gulp-sdk` and `gulp-cli` are separate
projects with independent versions and publication workflows.

## During development

Keep `CHANGELOG.md` headed by `# Unreleased`. Record every completed change in
one of these sections without separating backend and frontend work:

- `Breaking Changes and Migrations`
- `Added`
- `Fixed`
- `Removed`

Create the `Unreleased` section if it is absent. The release workflow never
edits the changelog or selects the next version automatically.

No GitHub Actions workflow runs for branch pushes or pull requests. Developers
must run the relevant local backend and UI checks before preparing a release.

## Prepare a release

On `develop`, choose the final semantic version and rename the first changelog
heading. For example:

```text
# Unreleased
```

becomes:

```text
# v2.0.0
```

Complete all four categories. Under `Breaking Changes and Migrations`, include
the exact migration script and any required configuration changes, or state
`None.` when the release needs neither.

Commit the finalized changelog and all release content on `develop`. Do not
edit or commit `src/gulp/_version.py`; it is generated by `setuptools-scm`.

## Advance master and tag

`master` contains only the latest released commit. Advance it without creating
a release commit, create an annotated tag on that same commit, and push both
references atomically:

```bash
git checkout master
git merge --ff-only develop
git tag -a v2.0.0 -m "gULP v2.0.0"
git push --atomic origin master v2.0.0
```

The tag push is the only event that starts `.github/workflows/release.yml`. A
push to `develop`, `master`, or any other branch does not start a workflow.

## Automated validation and publication

Before publishing anything, the release workflow verifies that:

- the tag has the exact `vMAJOR.MINOR.PATCH` form;
- the tag is annotated (cryptographic signing is not required);
- the tag resolves to the current remote `master` head;
- the checkout is clean;
- the first changelog heading exactly matches the tag;
- `setuptools-scm` resolves the tag to the same Python version.

The workflow then builds and checks the React application and Python source
artifacts, verifies GitHub archive version discovery, and builds both Docker
images. React has no version file or build-time product version; it must query
the backend `/version` endpoint if it needs to display the version.

The images are first published with immutable release tags:

```text
mentatis/gulp-core:v2.0.0
mentatis/gulp-ui:v2.0.0
```

Both contain OCI labels for the semantic version, full source revision, and
repository URL. The workflow moves both `latest` aliases only after the two
versioned images succeed, then creates or updates the GitHub Release using the
matching changelog section as its release notes.

## Verify a release

Check the installed core:

```bash
gulp --version
```

The output includes the semantic version and the first six commit characters:

```text
gulp_2.0.0 (gabcdef)
```

The authenticated API `/version` returns the same string. Docker image
inspection must report `2.0.0` in `org.opencontainers.image.version` and the
full tag commit in `org.opencontainers.image.revision`.

GitHub's Source code archives do not contain `.git`. The committed
`.git_archival.txt` and `.gitattributes` entries preserve tag and commit
metadata so that `pip install .` from an extracted release archive generates
the same `_version.py` as a clone of the tag.
